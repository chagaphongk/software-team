# T0.5 and T1 playbook

## T0.5 — small path

`PLAN → BUILD → VERIFY → DONE`. The verifier is the sole checking role — its pass
includes the 5-category review (its own contract says so).

- The orchestrator drafts a compact plan itself: destination, files, 1–3 acceptance
  criteria, an `Out of scope:` line, the verify command — and **proceeds without a
  confirmation wait**: the human's own scoped request already authorizes reversible,
  low-judgment work.
- The moment drafting turns up a fork, a scope increase, or a failed T0.5 bar,
  reclassify as T1/T2 and restart Step 2 — never force it into T0.5.
- Spawn one `software-team:builder` at the sonnet floor (`Mode: TDD` for a bug fix),
  then `software-team:verifier` against the stated criteria.
- A VERIFY `FAIL` re-enters BUILD → VERIFY, counted against the shared 3-round cap
  below. If a fix round escalates the builder to opus, `references/model-routing.md`'s
  escalation rules apply exactly as on any tier.
- No researcher, no Fable, no decision-log entry.

## T1 — standard path

`RESEARCH → PLAN → BUILD → VERIFY → DONE`.

- Researcher only when context is non-obvious — but always for a bug
  (`references/debugging-before-plan.md`: its confirmed root cause and regression test
  feed PLAN).
- Builder per `references/model-routing.md`; `Mode: TDD` whenever the plan calls for
  TDD or the task is a bug fix (the regression test is the first red step).
- Verifier always — its pass includes the 5-category review checklist on any
  non-mechanical logic change (its own contract says when); there is no separate
  reviewer spawn.

## PLAN output shape (T1/T2)

First size it: if you can't state a Destination in one or two lines without hedging, or
drafting turns up more than two or three genuine forks, or a fork's resolution needs
investigation spanning more than this session — go to `references/plan-sizing.md`
instead of forcing an oversized plan. Otherwise:

1. **Destination** — one line: what "done" looks like.
2. **Settled constraints** — not reopenable without a scope change.
3. **Steps** — each marked *ratification* (follows from a settled constraint) or *fork*
   (options genuinely diverge — put it to the human: 2–4 concrete options, one
   recommended, each with the cost it accepts; never answered for them).
4. **Acceptance criteria** — testable statements, copied verbatim into every spawn.
5. **Out of scope** — files/behaviors that must not change.

## The confirmation rule

Present the plan. **Wait for explicit confirmation** when any of these holds: the plan
contains a fork; the request was unsettled or the plan widens/changes its scope; the
tier is T2 (always — see `references/t2.md`). Revise-and-present as many rounds as it
takes; never build on silence or an implicit signal, and approval of an earlier
revision never carries to a later one.

**Proceed without waiting** when the request was settled and scoped, the work is
reversible, and the plan holds only ratifications — the human's own request authorizes
it; present the plan and continue in the same turn. Any doubt → wait.

## When BUILD/REVIEW/VERIFY can't converge

Cap the loop at 3 rounds total, shared across a review `CHANGES REQUIRED` (T2's Fable
pass), VERIFY `FAIL`, and VERIFY `BLOCKED` — the same signal: the team couldn't close the loop that round. At
the cap, stop and give the human a real choice: what got fixed each round, what's
unresolved, and (a) force-approve, explicitly marked unverified (b) more guidance,
counter resets to 0 (c) cut scope or change approach, back to PLAN. Never loop past the
cap, and never pick (a) yourself.

- **BLOCKED never resolves into a verdict at your hand.** If you execute a BLOCKED
  verifier's run-it-yourself checklist, re-spawn the verifier with the real output —
  the verdict is always its call.
- **A fix-round re-spawn is not a cold start** — its `Context:` carries the prior
  round's verdict findings verbatim plus the prior builder's files-changed list.
